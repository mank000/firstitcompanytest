# Чек на удачу

## О проекте

Небольшое приложение промо-акции. Покупатель регистрирует чек, модератор проверяет его в Django admin, а покупатель видит результат в личном кабинете.

## Стек

Python 3.14, Django 6.1, PostgreSQL 17, Docker Compose, uv, Django templates, vanilla JavaScript и обычный CSS.

## Запуск

1. Скопируйте `.env.example` в `.env` и задайте свои `POSTGRES_PASSWORD` и `DJANGO_SECRET_KEY`. Даты акции укажите в формате `ГГГГ-ММ-ДД`.
2. Запустите `docker compose up --build`.
3. Откройте [http://localhost:8000](http://localhost:8000) и зарегистрируйте покупателя.
4. Для доступа модератора выполните `docker compose exec web python manage.py createsuperuser` и откройте [http://localhost:8000/admin/](http://localhost:8000/admin/).

Миграции выполняются при запуске контейнера. Для повторного запуска достаточно `docker compose up`. Чтобы начать с пустой базой, используйте `docker compose down -v`, затем `docker compose up --build`. Команда `down -v` удаляет данные базы этого Compose-проекта.

Проверки внутри контейнера:

```bash
docker compose exec web python manage.py check
docker compose exec web pytest -q
docker compose exec web ruff check .
docker compose exec web python manage.py makemigrations --check --dry-run
```

## Что реализовано

- Регистрация, вход и выход через стандартный Django auth. После входа открывается личный кабинет.
- Регистрация чека через `fetch` без перезагрузки страницы. Ошибки показываются рядом с полями, успешная отправка — отдельным состоянием формы.
- Серверная проверка цифровых ФН, ФД и ФП, суммы от 1000 ₽, даты покупки в период акции и уникальности сочетания ФН + ФД + ФП. На уровне базы есть `UniqueConstraint`.
- Новый чек создаётся со статусом `pending`; пользователь не передаёт владельца, статус, причину отказа и дату регистрации.
- Личный кабинет показывает только свои чеки, отсортированные от новых к старым, по 10 на страницу.
- Модератор ищет чеки по ФН, ФД, ФП и имени пользователя, фильтрует по статусу, меняет статус и указывает причину отказа в Django admin.
- `GET /api/receipts/` возвращает JSON с чеками только текущего пользователя. Неизвестные параметры дают 400, другие методы — 405.
- Адаптивные страницы регистрации чека и кабинета, в том числе для ширины 375px.

## Дополнительные функции

- Тесты ключевой валидации, доступа к чекам, API и модерации.
- При отказе admin требует причину; при смене статуса на другой причина очищается.

Разбор QR, фото чека, автоматическое обновление статуса и CSV-выгрузка не добавлены.

## Спорные решения

- Отклонённый чек нельзя зарегистрировать повторно: ФН + ФД + ФП идентифицируют тот же физический чек. Проверка есть в форме и базе; ошибка базы при одновременной отправке преобразуется в понятный ответ.
- Начальная и конечная даты акции включены. Значения читаются из `.env` и преобразуются в `date` в настройках.
- Часовой пояс акции — `Europe/Moscow`. Введённые дата и время покупки трактуются в этом поясе, и календарный день сравнивается с границами акции в нём. Пользователю в другом поясе нужно вводить время чека по московскому времени; пересчёта из часового пояса браузера нет.
- Неизвестные параметры API отклоняются, чтобы клиент не мог выбирать владельца чека.

## Работа с ИИ

ИИ помог сверить требования с существующим кодом, подготовить тесты и адаптировать страницы по скриншотам макета. В первом варианте API POST без CSRF-токена возвращал 403 вместо требуемого 405; это обнаружилось при проверке обычным HTTP-запросом и было исправлено. Если бы было больше времени, я бы добавил автоматические браузерные проверки основных сценариев и разбор строки QR-кода.

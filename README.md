# Чек на удачу

## О проекте

Небольшое приложение промо-акции. Покупатель регистрирует чек, модератор проверяет его в Django admin, а покупатель видит результат в личном кабинете.

## Стек

Python 3.14, Django 6.1, PostgreSQL 17, Docker Compose, uv, Django templates, vanilla JavaScript, обычный CSS, Segno для QR-кодов и Pillow для проверки фото.

## Запуск

1. Скопируйте `.env.example` в `.env` и задайте свои `POSTGRES_PASSWORD` и `DJANGO_SECRET_KEY`. Даты акции укажите в формате `ГГГГ-ММ-ДД`.
2. Запустите `docker compose up --build`.
3. Откройте [http://localhost:8000](http://localhost:8000) и зарегистрируйте покупателя.
4. Зарегистрируйте обычного пользователя `moderator` через сайт и включите ему флаг `is_staff`: `docker compose exec web python manage.py shell -c "from django.contrib.auth.models import User; User.objects.filter(username='moderator').update(is_staff=True)"`. После этого войдите под ним на [http://localhost:8000/admin/](http://localhost:8000/admin/). Другие права или статус суперпользователя для проверки чеков не нужны.

Миграции выполняются при запуске контейнера. Для повторного запуска достаточно `docker compose up`. Фото хранятся в отдельном Docker volume. Чтобы начать с пустой базой, используйте `docker compose down -v`, затем `docker compose up --build`. Команда `down -v` удаляет базу и загруженные фото этого Compose-проекта.

Проверки внутри контейнера:

```bash
docker compose exec web python manage.py check
docker compose exec web pytest -q
docker compose exec web ruff check .
docker compose exec web python manage.py makemigrations --check --dry-run
```

## Что реализовано

- Регистрация, вход и выход через стандартный Django auth. После входа открывается личный кабинет.
- В шапке доступны правила акции и профиль с выходом из учётной записи.
- Регистрация чека через `fetch` без перезагрузки страницы. Ошибки показываются рядом с полями, успешная отправка — отдельным состоянием формы.
- Серверная проверка цифровых ФН, ФД и ФП, суммы от 1000 руб, даты покупки в период акции и уникальности сочетания ФН + ФД + ФП. На уровне базы есть `UniqueConstraint`.
- Период акции выводится из настроек на форме регистрации, в личном кабинете и на странице правил.
- Новый чек создаётся со статусом `pending`; пользователь не передаёт владельца, статус, причину отказа и дату регистрации.
- Личный кабинет показывает только свои чеки по 10 на страницу. По умолчанию новые идут первыми; заголовки даты покупки, статуса, суммы и даты регистрации переключают направление сортировки.
- Модератору достаточно флага `is_staff`: он ищет чеки по ФН, ФД, ФП и имени пользователя, фильтрует по статусу, меняет статус и указывает причину отказа в Django admin. В списке есть быстрые кнопки для принятия и отклонения чека.
- `GET /api/receipts/` возвращает JSON с чеками только текущего пользователя, включая отдельные `purchase_date` и `purchase_time`. Неизвестные параметры дают 400, другие методы — 405.
- Адаптивные страницы регистрации чека и кабинета, в том числе для ширины 375px.

## Дополнительные функции

- Тесты ключевой валидации, доступа к чекам, API и модерации.
- При отказе admin требует причину; при смене статуса на другой причина очищается.
- В форму можно вставить строку QR-кода `t=...&s=...&fn=...&i=...&fp=...`: дата, время, сумма и реквизиты чека заполняются автоматически, затем пользователь проверяет и отправляет форму.
- Сканирование QR-кода камерой заполняет поля чека без автоматической отправки. Ручной ввод остаётся доступным. Для камеры нужен браузер с `BarcodeDetector`, разрешение пользователя и HTTPS (либо `localhost` при локальной разработке).
- В кабинете и админке показан QR-код, собранный из сохранённых реквизитов чека.
- К чеку можно приложить фото JPG или PNG до 5 МБ. Формат и размер проверяются на сервере; фото открывается только владельцу или модератору с `is_staff`.
- Открытый кабинет проверяет изменения статусов через API каждые 30 секунд и после возвращения на вкладку. Статус и причину отказа он обновляет без перезагрузки.
- В кабинете можно скачать CSV только со своими принятыми чеками. В админке есть кнопка для выгрузки всех принятых чеков и отдельная ссылка в карточке пользователя для его чеков.
- Карточка пользователя в админке сокращена до учётных и личных данных, настроек доступа и ссылки на CSV; поля групп, индивидуальных прав и служебных дат скрыты.

## Спорные решения

- Отклонённый чек нельзя зарегистрировать повторно: ФН + ФД + ФП идентифицируют тот же физический чек. Проверка есть в форме и базе; ошибка базы при одновременной отправке преобразуется в понятный ответ.
- Дата и время покупки хранятся отдельно и показываются ровно как на чеке, без привязки к часовому поясу. Для участия дата на чеке сравнивается с границами акции включительно. Чек от 1 октября в 00:00 по Алтайскому краю попадает в акцию, если её начало — 1 октября. Дата регистрации `created_at` остаётся точным моментом времени; Django показывает его в часовом поясе `Europe/Moscow`.
- Исходная строка QR-кода не сохраняется, а чек можно внести вручную. Поэтому показанный QR содержит сохранённые дату, время, сумму, ФН, ФД и ФП, но не обязательно совпадает побайтно с кодом на бумажном чеке: в нём могли быть секунды, другой формат суммы или дополнительные параметры. Чужой QR-код пользователь открыть не может; модератор с `is_staff` видит его в админке.
- Фото необязательно. Оно хранится в отдельном volume и отдаётся через защищённый Django endpoint. Для обновления статусов выбран простой опрос API, поскольку мгновенная доставка через WebSocket для тестового задания не нужна.

## Работа с ИИ

ИИ помог сверить требования с существующим кодом, подготовить тесты, адаптировать страницы по скриншотам макета и разобраться с датами чеков. Предложенный перевод времени покупки между часовыми поясами усложнял проверку границ акции; после обсуждения дата и время покупки стали храниться так, как они указаны на чеке. В первом варианте API POST без CSRF-токена возвращал 403 вместо требуемого 405; это обнаружилось при проверке обычным HTTP-запросом и было исправлено.
